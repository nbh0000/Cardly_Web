# 인쇄물 편집기 — 구조 결정과 그 이유

`/print` 아래 여섯 갈래(홍보 전단지·쿠폰·포스터·현수막·배너·메뉴판)를 만드는
편집기의 뼈대입니다. 2차에서 템플릿을 대량으로 만들 사람이 읽을 문서라,
«무엇을 골랐는가» 보다 «왜 그것이어야 했는가» 를 적었습니다.

## 1. 기존 편집기를 늘리지 않고 새로 만들었다

먼저 명함 편집기(`components/studio/card-studio.tsx`)를 늘릴 수 있는지 봤습니다.
늘릴 수 없었습니다. 이유는 화면이 아니라 자료 구조에 있습니다.

명함·이력서·청첩장 편집기는 **칸이 정해진(fixed-slot)** 편집기입니다. 이름·직함·
전화번호처럼 미리 정해진 항목이 있고, 각 항목이 `useState` 하나씩을 차지하며,
어디에 놓일지는 템플릿의 CSS 가 정합니다. 사용자는 «무엇을 쓸지» 를 고르고
«어디에 둘지» 는 고르지 않습니다. 그래서 회전도, 겹침 순서도, 요소 추가도,
되돌리기도 없습니다 — 필요가 없었으니까요.

인쇄물은 반대입니다. 전단지에 무엇이 몇 개 들어갈지는 만드는 사람이 정합니다.
그러면 요소는 배열이어야 하고, 배열이면 선택·순서·묶음·되돌리기가 전부 따라
붙습니다. 이건 기존 편집기에 기능을 «더하는» 일이 아니라 자료 구조를 갈아
엎는 일이고, 갈아엎으면 잘 돌아가던 명함·이력서·청첩장이 함께 위험해집니다.

그래서 `lib/print/` 와 `components/print/` 를 따로 두었습니다. 기존 편집기
코드는 한 줄도 건드리지 않았습니다.

## 2. 좌표는 전부 mm, 글자 크기만 pt

화면 픽셀을 저장하지 않습니다. 저장된 문서에 든 값은 종이 위의 밀리미터이고,
픽셀은 그리는 순간에만 만듭니다(`scale`, px/mm).

픽셀로 저장하면 «어느 배율에서의 픽셀인가» 를 항상 함께 기억해야 합니다.
편집 화면은 62%로 축소해 보고 있는데 내보내기는 300dpi 라면, 그 사이 어딘가에서
반드시 계산이 어긋납니다. mm 로 들고 있으면 A4 로 만든 것을 A3 로 바꿔도 위치가
그대로고, 300dpi 든 150dpi 든 같은 값에서 파일이 나옵니다.

글자만 pt 입니다. 인쇄소와는 pt 로 이야기하기 때문입니다(1pt = 1/72인치).

## 3. 규격은 코드가 아니라 설정 파일 하나에

`lib/print/specs.ts` 가 «무엇을 만들 수 있는가» 를 혼자 정합니다. 갈래, 크기,
재단 여백, 안전선, dpi, 양면 여부, 절취선까지 전부 여기 있습니다.

2차에서 만드는 템플릿은 크기를 직접 적지 않고 이 파일의 id 를 가리킵니다.
그래야 «A2 안전선을 5mm 에서 7mm 로 바꾸자» 같은 결정이 배열의 숫자 하나를
고치는 일로 끝납니다. 템플릿 200장에 흩어져 있으면 그 결정은 영원히 못 합니다.

## 4. 되돌리기는 변경분이 아니라 스냅샷

`lib/print/store.ts` 는 문서 전체를 통째로 쌓습니다(최대 60단계).

변경분(diff)으로 쌓는 쪽이 메모리에는 낫지만, 새 기능을 더할 때마다 되돌리기
코드를 함께 고쳐야 하고 그 짝이 어긋나는 순간 조용히 깨집니다. 요소 백 개짜리
문서도 JSON 으로 수십 KB 라, 스냅샷 60장이 몇 MB 를 넘지 않습니다. «어떤
변경이든 되돌릴 수 있다» 를 코드 한 줄로 보장하는 값으로 싼 편입니다.

대신 드래그는 한 칸으로 묶습니다. 마우스를 끄는 동안에는 `commit: false` 로
마지막 상태를 덮어쓰고, 손을 뗄 때 한 번만 단계를 만듭니다. 그러지 않으면
Ctrl+Z 를 백 번 눌러야 원래 자리로 돌아옵니다.

## 5. 편집은 작게 그리고, 내보내기만 실제 해상도로

현수막은 5000mm 입니다. 300dpi 로 치면 59,000픽셀이고, 그 크기의 DOM 은 어떤
브라우저도 감당하지 못합니다.

그래서 편집 화면은 긴 변이 1200px 을 넘지 않도록 줄여 그리고(`editorScale`),
저장할 때만 실제 해상도로 다시 그립니다. 좌표가 mm 라서 이게 가능합니다 —
같은 문서에 다른 `scale` 을 곱하면 그만입니다.

같은 이유로 화면과 PNG 내보내기가 **같은 컴포넌트**(`ElementView`)를 씁니다.
미리보기용과 결과물용을 따로 그리면 언젠가 반드시 서로 달라지고, 그 차이는
인쇄를 맡긴 뒤에 발견됩니다.

## 6. PDF 는 벡터, PNG·JPG 는 래스터

기존 이력서·명함 내보내기(`lib/studio/export.ts`)는 html2canvas 로 화면을 찍어
jsPDF 에 그림으로 붙입니다. 화면과 100% 같다는 장점이 있지만 결과는 사진입니다.
확대하면 글자가 깨지고, 인쇄소에서 «벡터 파일 주세요» 라고 하면 줄 것이 없습니다.

인쇄물 PDF 는 `pdf-lib` 로 처음부터 다시 그립니다. 글자는 글자로, 도형은 도형으로
들어가고, 사진만 사진으로 들어갑니다. 페이지 크기는 mm 를 pt 로 바꾼 실제 규격이고,
재단 여백과 재단 표시(crop marks)를 선택할 수 있습니다.

대가는 하나 남았습니다 — 줄바꿈 위치를 브라우저가 아니라 우리가 계산하므로
화면과 미세하게 다를 수 있습니다. 내보내기 화면에서 그대로 알립니다.

처음에는 대가가 둘이었습니다. PDF 에 심을 수 있는 글꼴이 한 벌뿐이라 나머지
다섯 벌은 자형이 바뀌었습니다. 돈을 받고 파는 인쇄물에서 «화면과 다른 글꼴로
찍히는 것» 은 결함이라, 글꼴 목록을 «PDF 에 심을 수 있는 여섯 벌» 로 다시
짰습니다. 지금은 화면과 PDF 가 같습니다. 사정은 `docs/print-fonts.md`.

## 7. Gemini 는 반드시 서버를 거친다

API 키는 서버 환경변수(`GEMINI_API_KEY`)로만 삽니다. 이 사이트는 정적 내보내기라
Next.js 서버 라우트가 없으므로, 서버 역할은 Supabase 엣지 함수
(`supabase/functions/ai-print/`)가 맡습니다. 클라이언트는 `lib/print/ai.ts` 를
통해 그 함수만 부릅니다.

키를 클라이언트에 두면 누구나 개발자 도구에서 꺼내 쓸 수 있고, 그 비용은 우리가
냅니다. 서버를 거치므로 크레딧 차감·일일 한도·요청 로그도 같은 자리에서 됩니다.

## 8. 템플릿은 «판» 이 아니라 «자와 연필» 로 짭니다

마흔여덟 장을 함수 하나로 찍어 내면 마흔여덟 장이 다 똑같아 보입니다. 그건
«AI 가 만든 티» 가 가장 잘 나는 지점입니다. 그렇다고 손으로 다 적으면 같은
말이 마흔여덟 번 반복됩니다.

그래서 `templates/kit.ts` 에는 되풀이되는 잡일만 두었습니다 — 규격 찾기,
요소 번호 매기기, 그림 주소 잇기, 없는 그림 걸러내기, 이름과 값을 좌우로
벌린 한 줄(`priceRow`). 짜임은 각 템플릿이 직접 적습니다.

요소 id 를 무작위로 주지 않고 `<템플릿아이디>-1` 처럼 순서대로 붙이는 것도
같은 이유입니다. 무작위면 서버에서 그린 것과 브라우저에서 그린 것이 달라지고,
무엇보다 «어느 요소가 문제인가» 를 사람이 말할 수 없게 됩니다.

자세한 것은 `docs/print-templates.md` 에 있습니다.

## 9. 인쇄물은 링크가 아니라 파일을 팝니다

청첩장·초대장은 «링크» 를 팔고, 그래서 기한이 있습니다. 링크가 살아 있는
동안 사진과 글을 우리가 보관하니 비용이 계속 들기 때문입니다.

인쇄물은 «파일» 을 팝니다. 한 번 내려받으면 끝이라 보관 비용이 없고, 그래서
기한도 두지 않았습니다. 데이터베이스에서도 인쇄물만 `expires_at` 을 null 로
둡니다(`mark_order_paid`).

막는 방식도 다릅니다. 결제 전에도 편집과 내보내기가 **전부** 됩니다 — 다만
결과물에 «Cardly 미리보기» 표시가 옅게 깔립니다. 내려받지 못하게 막는 쪽이
매출에는 나을 것 같지만 실제로는 반대입니다. 인쇄물은 «내가 만든 것이 진짜
그럴듯한가» 를 확인해야 지갑을 열고, 확인할 방법이 없으면 그냥 떠납니다.

표시를 지울 줄 아는 사람이 있다는 것도 압니다. 그건 감수합니다 — 그 사람을
막으려고 나머지 모두를 불편하게 만드는 쪽이 훨씬 손해입니다.
